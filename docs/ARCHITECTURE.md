# Целевая архитектура Flow Space

## Основные сущности

- **User** — человек с личным пространством и членством в компаниях.
- **Company** — изолированный контур команды, настроек и аналитики.
- **Outcome** — ожидаемый бизнес-результат.
- **Success Criterion** — проверяемое условие приёмки результата.
- **Task** — работа, необходимая для достижения Outcome.
- **SOP** — версионируемый регламент, связанный с типами задач.
- **Review** — решение о принятии результата или возврате с причиной.
- **Metric** — SLA, доля приёмки с первого раза, просрочки и перегрузка.
- **Risk Signal** — объяснимый сигнал AI с источником и рекомендуемым действием.
- **Executive Summary** — периодическая сводка для собственника.

## Изоляция данных

Личные и корпоративные данные должны храниться в разных коллекциях/контурах:

- `users/{userId}/personal/*`;
- `companies/{companyId}/*`;
- членство пользователя хранит роль, но не переносит личные задачи в компанию.

Firestore rules должны запрещать чтение личного контура любому другому пользователю, включая владельца компании.

## Минимальная модель Outcome

```json
{
  "title": "Запустить новую посадочную страницу",
  "expectedResult": "Страница опубликована и принимает заявки",
  "successCriteria": [
    "форма создаёт лид в CRM",
    "мобильный Lighthouse Performance >= 80",
    "аналитика фиксирует отправку формы"
  ],
  "ownerId": "user-id",
  "dueAt": "ISO-8601",
  "status": "planned|in_progress|review|accepted|blocked",
  "sopId": "optional",
  "companyId": "company-id"
}
```

## Порядок внедрения

1. Разделить My Space и Company Space на уровне данных и правил доступа.
2. Добавить ожидаемый результат и критерии успеха в карточку задачи.
3. Сделать этап Review настоящей приёмкой результата с причиной возврата.
4. Рассчитывать SLA и First-pass acceptance из событий, а не вручную.
5. Добавить объяснимые Risk Signals.
6. Собрать Executive Summary и рекомендации по делегированию.
